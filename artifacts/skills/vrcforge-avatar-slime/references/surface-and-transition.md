# 表面、过渡与问题处理

本页从实际 Slime 制作、用户指出的问题和下列官方资料归纳操作方法。实际案例的观察用于选择排查方向；字段、数值和成功结论仍以本次模型为准。这里没有预设头像路径、队列常数或一键覆盖表。

## 1. 先确定要做成什么样

参考图要实际打开看。重点提取圆润发束、成块高光、清晰五官、身体透过程度、服装与胶体的对比，而不是只看画中主色。插画的透视不一定能由当前实时 Shader 重现。

已有约定直接执行；用户已指定 Slime 颜色、透明部位和正常外观时分别记录，新模型不自动继承上一次的选择。用户说“透明度高一些”时降低对应部位的不透明度，不顺带把眼睛、口腔、衣服都改成透明。

| 部位 | 操作与检查 |
| --- | --- |
| 身体、脖子、胸下与四肢 | 从实际 Renderer/slot 检查完整皮肤覆盖；身体透明，但轮廓与体积仍可辨。 |
| 头部皮肤 | 比身体更不透明，保留光泽、水波和可见透过；单独处理内部口腔、备用表情。 |
| 眼睛、睫毛、真实表情 | 保持原有五官可读，不随 Slime 肤色整张染色，不关闭原有表情驱动。 |
| 头发、耳、尾巴 | 依实际网格纳入同一开关；保留发束/尾尖的 alpha 轮廓，耳饰等装饰不凭名字覆盖。 |
| 服装、镜片、饰品 | 根据用户目标保留；透明镜片与 Slime 脸分开排查，不默认所有东西一起 Slime 化。 |

## 2. 轻量水波要真的动，底图要保持原位

1. 从源材质复制工作材质，确认普通透明模式、底色/alpha、法线槽和光泽功能实际存在。先做静止胶体表面，再加动画，便于判断哪项产生缺陷。
   如果降低颜色 alpha 却没有变得更透明，先读最终 alpha 的来源：Alpha Mask 的“替换”和“乘算”对颜色 alpha 的作用不同，不反复盲改同一个颜色值。[Alpha Mask 模式](https://lilxyzw.github.io/lilToon/ja_JP/color/alphamask.html)。
2. 优先复用一张平铺、可循环的波纹法线。导入类型为法线，纹理按实际需要 Repeat；颜色、面部图集与遮罩继续留在各自用途。读取当前导入状态，按报告处理 Mip Streaming；无需为水波自动升级 Shader。
3. 以适度法线强度配合光泽、边缘反射，让高光随法线变化形成水面感。只换 normal 而未启用相关光照特征，可能几乎看不到变化。避免用强金属反射或大面积发光代替湿润感。
4. **先查 UV 的作用范围。** lilToon 当前公开实现第一法线采样使用 `uvMain`，第二法线从所选原始 UV 加各自纹理变换采样。滚动主 UV 可能连五官/皮肤遮罩一起移动；第二法线也不能凭空假定有独立 Scroll 字段。字段以当前版本实际 Shader 与工具返回为准。[法线实现](https://github.com/lilxyzw/lilToon/blob/master/Assets/lilToon/Shader/Includes/lil_common_frag.hlsl)、[UV 文档](https://lilxyzw.github.io/lilToon/ja_JP/base/uv.html)。
5. 需要独立水波时，优先给法线纹理自身的 Offset/变换写动画，保留 Tiling；也可复用现场已存在且作用范围正确的 UV 动画。使用精确绑定读取确认工具能写该属性，不猜绑定路径。法线与主图共享 UV 时，选已支持的分离方式，不能拿整个脸一起滑动冒充成功。
6. 检查纹理变换的全部分量：Tiling 非零，Offset 确实随时间变化。实际曾有偏移在动、缩放却被动画清零的问题；修正缩放并运行开关才恢复水波，单帧截图发现不了这类缺陷。第二法线曾用于把水波与底图分开，但不继承那次各部位的平铺数字。
7. 循环 Offset 从起点移到纹理周期等价的位置，以平铺纹理完成接缝循环，曲线保持匀速，避免尾帧回跳。检查慢速播放、多周期和不同部位接缝。退出 Slime 时水波停用/恢复原值，再进入时确认继续正常。需要制作新法线时，可沿用周期高度场及其导数生成可平铺波纹的思路；不照搬特定头像 UV 遮罩，不把生成一张纹理当成帧率证明。

采用“普通透明 + 少量法线采样 + 光泽”的优先级，是结合低开销目标和已用配置作出的选择。真实折射会改变背景采样；只在用户确实需要这种光学扭曲时再采用。[光泽](https://lilxyzw.github.io/lilToon/ja_JP/reflections/reflection.html)、[法线](https://lilxyzw.github.io/lilToon/ja_JP/reflections/normal.html)、[折射](https://lilxyzw.github.io/lilToon/ja_JP/advanced/refraction.html)。

## 3. 平滑变身要把材质替换与连续曲线接起来

MA Material Setter 在承载对象启用时替换 Renderer 材质；它本身不承诺插值。现有 MA 能完成材质选择时继续用，不因一处工具错误就再复制整套常驻身体。[MA Material Setter](https://modular-avatar.nadena.dev/docs/reference/reaction/material-setter)。

1. 列出每个受影响槽的正常材质、Slime 材质、颜色/alpha/法线/反射等端点，以及实际写它们的 MA/FX/动画来源。参数、菜单按已有约定复用。
2. 连续属性在兼容材质内插值；材质引用、Shader 模式等离散项在预定时点切换。若先换材质，Slime 材质的起点必须能与切换前接上；若先反向还原，等还原到匹配端点再恢复正常材质。没有相容端点时，先明确设计可见变身方式，不把引用瞬换说成平滑。
3. 写完整 RGBA/XYZW 和双向端点；从现有状态继承的分量要明确保留。曾出现 alpha 曲线存档成功但运行 RGB 变黑，修正应针对完整颜色端点，而不是继续只核对 `.a`。
4. 检查进入、稳定、退出、半途反向，以及快速开关时是否从当前值过渡。不要把每次切换重置成固定起点而造成跳变；使用当前 Animator 实际支持的过渡和中断设置，避免两条驱动争写。
5. 同一 Renderer 的运行值可能由 PropertyBlock 覆盖。对照实际运行画面、工具提供的运行值与当前状态，不能只用磁盘 `.mat` 的颜色证明过渡正确。[Unity MaterialPropertyBlock](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/MaterialPropertyBlock.html)。
6. 观察身体、头、发束、尾巴是否同步；正常状态应恢复该状态原有材质、UV 和透明度。Slime 动画只写需要的表面属性，不复制其它外观功能的基线曲线，也不在此扩做独立功能。

## 4. Slime 实际出现过的缺陷怎么定位

### 脖子或胸下残留肉色

先区分是漏掉的皮肤材质槽、底图/第二层皮肤颜色、遮罩未覆盖，还是动画在局部重新写回正常色。实际案例的残留来自第二层皮肤；补它的 Alpha 曲线后又遇到 RGB 清零，显式保留 RGB 后进行了双向过渡采样。按正常、Slime 静止、过渡中途三种状态定位；对照 UV 图集确认区域后再改。不要为了补一小块皮肤把虹膜、口腔和整张图集全部染色。

### 刘海缺了一块，露出粉色断面

实际案例中，变身材质被排到作者 FakeShadow 后面，恢复作者头发与投影的相对顺序后正面缺口消失，并检查了正常/Slime 切换。可复用的是相对绘制关系，不是那次的队列数值。

读脸、发、FakeShadow 的有效队列和 Stencil；作者方案让脸写入某个非零标记、头发清除对应区域、投影只在该标记区域显示。先核对当前配置是否采用这套关系，再调有关层，不默认给任意模型套同一 ID，不删除阴影层。[FakeShadow 官方配置](https://lilxyzw.github.io/lilToon/ja_JP/base/fakeshadow.html)、[Stencil](https://lilxyzw.github.io/lilToon/ja_JP/advanced/stencil.html)。

### 眼镜镜片反光、挡住眼睛或头发

先隔离镜片判断是反射太强、折射采样还是深度/排序。在无需扭曲背景的案例中，独立普通透明镜片工作材质、降低遮挡并保留轻反光解决了可见问题。实际参数依镜片厚度、alpha 和队列决定，不能把“眼睛异常”直接当成虹膜颜色问题。

### 备用眼片、牙齿、口腔从脸或后脑透出

1. 透明外壳会暴露正常不透明皮肤原先遮住的内部几何。先读真实表情驱动和子材质；检查 idle、使用中的表情、眨眼、张嘴及面捕，而不是直接删备用片或禁用面捕。
2. 如果原本应该隐藏的片仍被绘制，先修它的当前显隐/alpha/深度/排序来源。如果片确实需要显示，只是透过皮肤时泄露，则需要按实际拓扑选局部更高 alpha、合适深度覆盖或局部 Stencil；局部纹理 mask 管单材质，Stencil 管跨材质关系，不能混为一谈。[Alpha Mask](https://lilxyzw.github.io/lilToon/ja_JP/color/alphamask.html)、[Stencil](https://lilxyzw.github.io/lilToon/ja_JP/advanced/stencil.html)。
3. 旧版头部曾用双面深度预写改善后脑口腔，Unity 背面和穿入测试有完成记录。后续正面备用表情是另一轮问题：候选把外壳深度写入排在内表情之前，Unity 检查保留了主动表情。它们是两项有不同验证范围的实际案例；不继承那次的队列数字，也不把旧版后脑通过说成新版正面通过。
4. 深度预写和提高不透明度可能连用户希望看到的穿入手臂一起挡掉；不能只因内部表情消失就判通过。必须同时保留外部测试物的透过目标、正常表情和用户要求的头部透明感。
5. 会话中曾出现 Unity 捕获未复现、用户在 VRChat 正面仍看得到的情况；候选写入和 Unity 主动表情截图之后，客户端问题仍待验收。因此 Scene、Game、客户端显示路径要分开记录；Unity 通过不能关闭已有客户端问题。

## 5. 验证透明目标和性能

用已授权正常比较头像或测试物穿过身体，正面和斜侧都应能看到内部轮廓；透明叠层会影响排序，不用单张正面图代替。测试完保留/恢复用户约定的状态，实际把截图或短视频发给用户。

多角度检查整体以及脸、后脑、脖子、胸下、发束、尾巴和镜片的疑点；表情及与现有外观的直接交互按影响范围抽查，已有正确结果不重复做。独立衣柜、体型或物理修正不在本 Skill 中展开。发布到 VRChat 后，对好友手臂、镜子/相机和开关同步分别标记实际验证情况；未进入客户端不声称已验收。

以正常/Slime 同视角比较增加的材质槽、Pass、透明覆盖面积和可用帧时数据；Performance Rank 不覆盖所有 Shader 成本。减少多层整身透明壳和不需要的折射/模糊，不能只凭“贴图小”就称省性能。[VRChat 优化建议](https://creators.vrchat.com/avatars/avatar-optimizing-tips/)、[Performance Rank 的范围](https://creators.vrchat.com/avatars/avatar-performance-ranking-system/)。

## 使用资料的方式

每条外链支持相邻的机制说明，不代表官方保证整套 Slime 效果。Shader 属性和 MA 行为按现场版本复核；插画只作美术参考，用户纠正和实际运行结果优先。导入回执不明时读取原任务与已落地资产；不要重复导入、创建替身工具或靠源码 Shell 操作 Unity 来绕过产品缺口。
