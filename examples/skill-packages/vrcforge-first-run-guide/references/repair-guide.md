# Current setup and repair routes

This is Agent guidance for existing tools, not a new automation engine. Always discover the actual schema. Do not infer argument values, confirmation tokens, project identities or package hashes from examples.

## ALCOM, VCC and an empty Unity project

Follow the failing layer, not a fixed checklist on every turn. Reuse facts already read and state the next useful action. Ordinary Unity work does not require a VRChat SDK or Avatar Descriptor; check those only for the requested VRChat workflow.

1. **Identify the project and task.** Use the selected project and its existing status. If needed, read `ProjectSettings/ProjectVersion.txt` and the package files through the exposed `vrcforge_read_text_file` / `vrcforge_list_directory`. These are backend file reads, not Unity Core calls. Read the returned first page, note total size/completeness, and continue only when the unread part matters. Do not ask an installed-App user to find VRCForge source code or run development commands.
2. **Separate project, SDK, Core and model.** VCC/ALCOM Avatar templates prepare project packages; they do not prove the user's model is in the scene or has a `VRC Avatar Descriptor`. A Unity Hub empty project need not contain VRChat packages at all. A package declaration is not proof it resolved or compiled. For Avatar work, inspect `com.vrchat.avatars` and `com.vrchat.base` using the observed package/Doctor results or a read-only `vrcforge_package_install_plan` for the exact package. Do not infer SDK presence from a package-status response that lists only optional addons. Do not add MA/VRCFury unless the model or operation needs them.
3. **If Core cannot answer, stay on the host side.** Use App diagnostics, `vrcforge_core_upgrade_status`, package status/plan and the project package files. `vrcforge_diagnose_package_install_errors` can retain a failed compile-reader result; that failure is not evidence that there are no compile errors. Read available logs or guide the user to Unity's Console → menu → Open Editor Log, then inspect the actual error. Do not loop on `list_avatars`, scene tools or the failed Core compile reader. Resolve a proven missing package or compile failure before retrying the blocked tool; do not reinstall Core to fix an absent SDK.
4. **Install only the missing dependency through the existing plan.** Keep the user's ALCOM/VCC choice. Review `packageState`, `compatibilityAction`, `executionStrategy` and `canExecuteCommandInstall` from the plan. `use_installed` means use the installed version; a missing dependency is not permission to upgrade everything. If the discovered vrc-get command path supports this plan and the user authorized repair, continue through the existing supervised install: internal `vrcforge_package_install_request` / approval flow, or external `vrcforge_install_vpm_package` and its returned confirmation. Preserve checkpoint and execution receipts. Do not treat a request or UI handoff as an executed install, bypass it with manifest edits, or retry a pending operation.
5. **When the plan needs UI, give one concrete action.** VCC: Projects → Add Existing Project → select this project root → Manage Project → locate the missing package and install the compatible version. For a genuinely new project: New → Avatar → name/location → Create Project. ALCOM: use its current Projects/add-existing or create-project screen, select the same root or Avatar template, then that project's package-management screen; verify the displayed buttons rather than invent VCC-equivalent labels. Tell the user the exact project/package and the expected installed entry, then read state again. If a manager, supported editor, login or license is missing, follow `references/zero-start.md`; do not require both managers or recreate a working project.
6. **After packages compile, check the actual target.** Read the intended scene/model. If no model is present, open the author's scene or place its prefab after the relevant authorization; do not keep scanning an empty scene. If the model exists but lacks a Descriptor, explain that this is a model-component issue, not SDK installation failure. Use the existing authorized Avatar/component workflow if exposed, otherwise guide selection of the correct model root → Inspector → Add Component → VRC Avatar Descriptor and its required settings. Leave diagnosis-only scope before avatar writes. Read the result and retry the original requested operation; installed SDK alone is not avatar acceptance.

Sources: [ALCOM author's site](https://vrc-get.anatawa12.com/en/alcom/) explains shared VCC settings and its relationship to the [vrc-get implementation](https://github.com/vrc-get/vrc-get); [VCC package manager](https://vcc.docs.vrchat.com/vpm/) documents templates and existing-project management; [VRChat first-avatar guide](https://creators.vrchat.com/avatars/creating-your-first-avatar/) separates SDK setup, scene model and Descriptor; [current VRChat Unity version](https://creators.vrchat.com/sdk/upgrade/current-unity-version/) and [Unity log locations](https://docs.unity3d.com/2022.3/Documentation/Manual/LogFiles.html) provide version-specific instructions. Recheck the relevant current page rather than hardcoding a future editor/package version.

## Other setup and repair routes

| Observed problem | Available action | Evidence required afterward |
| --- | --- | --- |
| Internal model cannot answer/test fails | App model settings and explicit connection test; explain actual auth/endpoint/model/quota/network error | A successful test for that exact configuration, not just saved settings |
| External Agent works, App provider is unconfigured | Keep external provider; report App provider gap as not applicable to that client | Authenticated MCP plus all project/Core/compile checks |
| Gateway cannot list tools | Guide App start, Gateway enable and client configuration reload | Real initialize/tools-list response; no write through a dead connection |
| Project scan pending/error/empty | Read discovery state; refresh in App or ask for exact existing folder | Completed scan or validated manually supplied project root |
| Correct existing project not registered/selected | `vrcforge_register_project` / `vrcforge_select_project` | Independent selected-project readback, preserving previous selection on failure |
| Selected project not running | Ask user to open this exact project; no current MCP open-existing-project tool | Matching running editor and selected instance |
| Bundled Core missing/incomplete | `vrcforge_install_unity_core` with `projectPath`, subject to approval | Installation receipt, then status/compile/required-tool readback |
| Diagnosis confirms incomplete or mixed-version official Core files | Inspect the installed source/compile evidence and bundled repair scope, then request approval through `vrcforge_install_unity_core`; a still-callable old assembly does not prove the files on disk compile | Preserve installation receipt and backup; verify fresh compilation and `vrcforge_core_upgrade_status` before resuming the original task |
| Core copied but waiting | `vrcforge_core_upgrade_status` with `projectPath` | Distinguish core_unreachable, waiting_for_domain_reload, waiting_for_post_install_compile, ready |
| Connection matches wrong editor | Diagnose with `vrcforge_unity_status`; select intended project via supervised path | Same exact project and registered instance, not any live instance |
| SDK/package errors | `vrcforge_package_manager_status`, `vrcforge_package_install_plan`, `vrcforge_diagnose_package_install_errors` | Concrete missing/incompatible package evidence; only use an actually exposed approved installer after reviewing its plan |
| Compilation errors | `vrcforge_get_compile_errors` when Core is callable; otherwise App diagnostics / ask for exact Console error | Errors resolved and compilation finished; identify ownership before touching third-party code |
| Failed Core change needs recovery | `vrcforge_restore_unity_core` after separate approval | Exact `projectPath`, `backupPath`, `backupSha256`, `installedSha256` from the same installation receipt; restore result and fresh readiness |

For tool execution use the current discovered schemas, not this table as a request template. Core installation's known required input is `projectPath`. It installs bundled Core files; it is not evidence that a `.unitypackage` UI import occurred. Restore hashes must never be guessed or taken from a different installation.

Manual package route: obtain the matching VRCForge package from the installed distribution or its matching release, confirm the destination Unity project, then guide Assets → Import Package → Custom Package… → Import All. Preserve package provenance and recheck compilation and connection. Never download an unrelated “MCP for Unity” as a substitute.

After Core is already connected, ordinary content `.unitypackage` imports are a different workflow: inspect/plan, bind the exact execution target, then the exposed outfit-package importer if it supports the requested content. Its presence does not solve first-Core bootstrap. A returned import job ID means poll that job; it does not mean import complete.

Do not repeat writes after a timeout until their operation status is known. Preserve checkpoints and pending receipts. If the required tool is absent, say what is missing and provide one precise manual action, then re-read state. Do not advertise automatic Unity launch, automatic provider credential repair, arbitrary source repair or recovery of every possible third-party error as existing capability.

Keep logs local unless the user authorizes sharing. Never include tokens/Keys, Avatar names or full project paths in public reports. A support bundle still needs review before publication.
